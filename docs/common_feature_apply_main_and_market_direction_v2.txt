Investment Briefing Engine
main / market-direction-v2 공통 기능 양쪽 적용 방법
====================================================

1. 목적
-------

main 브랜치와 market-direction-v2 브랜치는 시장방향 계산 방식만 다르게 유지하고,
시장데이터 수집, 계좌/보유종목, 정기매수, 브리핑 공통 계약, Swagger, 오류 처리 같은
공통 기능은 동일한 커밋을 양쪽에 적용한다.

권장 방식은 다음과 같다.

  1) 공통 기능을 main에서 독립 커밋으로 개발한다.
  2) main을 검증하고 PUSH한다.
  3) market-direction-v2 전용 worktree에서 해당 커밋만 cherry-pick한다.
  4) V2 환경에서 다시 검증하고 market-direction-v2를 PUSH한다.

market-direction-v2 전체를 main에 merge하거나 main 전체를 V2에 무조건 merge하지 않는다.
V2 전용 시장방향 코드와 설정까지 반대편 브랜치로 섞일 수 있기 때문이다.


2. 기능 분류 기준
-----------------

[공통 기능]

- KRX/Yahoo/FRED 등 외부 데이터 공통 클라이언트
- 수집 Job, 재시도, timeout, 로그, 마스킹
- 계좌, 종목, 보유자산, 정기매수, 현금보유 관리
- 공통코드와 기준정보
- 브리핑 공통 데이터 계약과 화면
- Swagger/OpenAPI 문서
- 공통 예외 처리와 응답 형식
- 보안, Docker 기반, 공통 테스트
- V1/V2가 함께 사용하는 DB 테이블과 컬럼

[V2 전용 기능]

- Robust-Z 계산
- 시장방향 V2 Feature 계산
- V2 모델 상태, 품질, confidence 계산
- V2 전용 테이블/컬럼/인덱스
- V2 전용 API 또는 화면
- V2 전용 Docker Compose, 포트, DB, 스케줄 설정
- V1 fallback을 포함한 V2 선택 로직

[main 전용 기능]

- V1 시장방향 계산을 유지하기 위한 코드
- 운영 main 환경에서만 사용하는 설정
- V2가 아직 사용하지 않는 V1 전용 스케줄 또는 호환 코드

분류가 불명확하면 한 커밋에 공통 코드와 V2 전용 코드를 같이 넣지 않는다.
먼저 공통 기반 커밋을 만들고, 이어서 V2 전용 커밋을 별도로 만든다.


3. 권장 디렉터리 구성
---------------------

하나의 작업 디렉터리에서 브랜치를 계속 switch하는 것보다 Git worktree를 사용한다.

예시:

  F:\source\investment-briefing-engine       -> main
  F:\source\investment-briefing-engine-v2    -> market-direction-v2

V2 worktree가 없다면 main 작업 디렉터리에서 다음 명령으로 만든다.

  git fetch origin
  git worktree add F:\source\investment-briefing-engine-v2 market-direction-v2

로컬에 market-direction-v2 브랜치가 없다면:

  git fetch origin
  git worktree add -b market-direction-v2 `
    F:\source\investment-briefing-engine-v2 `
    origin/market-direction-v2

주의:

- 같은 브랜치를 두 worktree에서 동시에 checkout할 수 없다.
- main 작업 트리가 dirty인 상태에서 branch switch로 V2 작업을 시작하지 않는다.
- 각 worktree의 미추적 파일과 사용자 변경을 먼저 확인한다.


4. 공통 기능 개발 및 적용 절차
------------------------------

4.1 main 최신화

  cd F:\source\investment-briefing-engine
  git status --short
  git fetch origin
  git pull --ff-only origin main

사용자 변경이나 미추적 파일이 있으면 삭제하거나 덮어쓰지 않는다.


4.2 공통 기능 개발

공통 기능만 수정한다.

예:

- Swagger summary/tag 정리
- 외부 API retry 개선
- 정기매수 validation 개선
- 공통 데이터 수집기 개선

V2 전용 계산 코드는 이 단계에 포함하지 않는다.


4.3 main 검증

변경 위험에 맞춰 다음을 확인한다.

- Java compile/test
- Frontend build
- Flyway migration 검증
- Docker image build
- 관련 HTTP API
- DB 저장 결과
- Swagger operation 수와 summary 누락 여부


4.4 공통 기능을 독립 커밋으로 생성

  git status --short
  git diff --check
  git add <공통 기능 관련 파일만 명시>
  git diff --cached --check
  git diff --cached --stat
  git commit -m "feat: <공통 기능 설명>"

중요:

- git add . 사용을 피한다.
- V2 전용 파일이나 사용자 미추적 문서를 함께 stage하지 않는다.
- 서로 독립적인 기능은 서로 다른 커밋으로 나눈다.


4.5 main PUSH 및 배포

  git push origin main
  docker compose build backend
  docker compose up -d backend
  docker compose ps

실제 서비스 포트와 업무 API까지 검증한다.


4.6 V2 worktree 최신화

  cd F:\source\investment-briefing-engine-v2
  git status --short
  git fetch origin
  git pull --ff-only origin market-direction-v2


4.7 main의 공통 커밋을 V2에 적용

공통 커밋 SHA가 abc1234라면:

  git cherry-pick abc1234

공통 커밋이 여러 개이고 순서가 중요하면 오래된 커밋부터 적용한다.

  git cherry-pick abc1234
  git cherry-pick def5678

연속된 커밋 범위는 다음처럼 적용할 수 있지만, 범위 안에 V1/V2 전용 커밋이 없는지
반드시 먼저 확인한다.

  git log --oneline abc1234^..def5678
  git cherry-pick abc1234^..def5678


4.8 cherry-pick 충돌 처리

충돌이 발생하면:

  git status
  git diff --name-only --diff-filter=U

파일별 판단 기준:

- 공통 DTO/API 계약: main 변경을 기본으로 반영하되 V2 필드를 보존한다.
- 공통 Service: main의 버그 수정과 V2 계산 진입점을 모두 유지한다.
- application.yml: 공통 설정은 반영하고 V2 포트/DB/스케줄 설정은 보존한다.
- Docker Compose: V2 서비스명, 컨테이너명, 포트, DB, volume, network를 보존한다.
- Flyway: 이미 적용된 migration을 수정하지 않고 새 migration 번호 충돌을 해소한다.
- 문서: 공통 설명과 V2 전용 설명을 모두 유지한다.

충돌 수정 후:

  git add <충돌 해결 파일>
  git cherry-pick --continue

잘못된 커밋을 선택했거나 안전하게 해결할 수 없다면:

  git cherry-pick --abort

`--abort`는 현재 cherry-pick을 시작하기 전 상태로 돌아가는 용도다.


4.9 V2 검증 및 PUSH

V2에서는 main과 별도로 다음을 검증한다.

- 공통 기능 API가 동일하게 동작하는가
- V2 시장방향 계산이 그대로 동작하는가
- V1 fallback 계약이 깨지지 않았는가
- V2 전용 DB와 main DB가 분리되어 있는가
- V2 전용 포트와 컨테이너만 변경되는가
- V2 자동 스케줄이 main 운영 스케줄과 겹치지 않는가

검증 후:

  git push origin market-direction-v2

V2 배포는 반드시 V2 전용 Compose 파일과 프로젝트명을 사용한다.

예:

  docker compose -p investment-v2 -f docker-compose.v2.yml build backend
  docker compose -p investment-v2 -f docker-compose.v2.yml up -d backend
  docker compose -p investment-v2 -f docker-compose.v2.yml ps


5. 반대 방향 적용
-----------------

공통 기능을 먼저 market-direction-v2에서 발견하거나 수정한 경우에도 동일하다.

  1) V2 전용 변경과 공통 변경을 서로 다른 커밋으로 분리한다.
  2) market-direction-v2에서 공통 커밋을 PUSH한다.
  3) main worktree에서 그 공통 커밋만 cherry-pick한다.
  4) main 검증 후 main을 PUSH하고 배포한다.

예:

  cd F:\source\investment-briefing-engine
  git fetch origin
  git cherry-pick <V2에서 만든 공통 커밋 SHA>
  git push origin main

V2 전용 커밋은 main에 cherry-pick하지 않는다.


6. Flyway migration 공통 적용 규칙
----------------------------------

DB migration은 일반 소스보다 충돌 위험이 높다.

규칙:

- 어느 환경에도 적용되지 않은 migration만 양쪽에서 동일 파일로 공유할 수 있다.
- 한쪽 DB에 이미 적용된 migration은 내용이나 이름을 수정하지 않는다.
- 같은 버전 번호를 양쪽 브랜치에서 서로 다른 내용으로 사용하지 않는다.
- 번호 충돌이 발생하면 아직 적용되지 않은 쪽에 새 번호를 부여한다.
- 공통 테이블 변경과 V2 전용 테이블 변경을 서로 다른 migration으로 나눈다.
- cherry-pick 후 두 DB에서 Flyway validate와 migrate 결과를 각각 확인한다.

예:

  V113__add_common_collection_retry_columns.sql
  V114__add_v2_market_direction_features.sql

첫 번째는 양쪽 브랜치에 적용하고, 두 번째는 V2에만 적용한다.


7. 공통 API 계약 규칙
---------------------

같은 API를 main과 V2가 모두 제공한다면 다음은 동일하게 유지한다.

- HTTP method
- URL path
- Request DTO
- Response DTO
- 오류 코드
- null 처리
- 날짜/시간대(Asia/Seoul)
- Swagger summary와 tag

V2에서 추가 정보가 필요하면 기존 응답 의미를 바꾸지 말고 호환 가능한 optional 필드를
추가하거나 V2 전용 endpoint를 분리한다.

예:

  공통: GET /api/v1/dashboard
  V2 전용: GET /api/v2/market-direction/explanation


8. 금지할 적용 방식
-------------------

다음 방식은 사용하지 않는다.

- dirty worktree에서 강제 branch switch
- 검증 없이 market-direction-v2 전체를 main에 merge
- 공통 기능과 V2 계산 기능을 한 커밋에 혼합
- git add .로 사용자 파일까지 커밋
- 이미 적용된 Flyway migration 수정
- main과 V2가 같은 DB/volume/network/자동 스케줄을 공유
- 충돌을 무조건 ours/theirs 한쪽으로 일괄 해결
- main 검증 성공만으로 V2 검증을 생략


9. 권장 커밋 예시
-----------------

좋은 예:

  feat: add provider-specific retry configuration
  fix: normalize regular-buy schedule payload
  docs: document common API inventory
  feat: add V2 robust-z market direction model

앞의 세 커밋은 공통 적용 후보이고 마지막 커밋은 V2 전용이다.

나쁜 예:

  feat: update retry, V2 robust-z, compose ports and dashboard

이렇게 섞으면 일부만 cherry-pick하기 어렵고 충돌 위험이 커진다.

11. 최종 권장안
----------------

이 프로젝트에서는 다음 원칙을 표준으로 사용한다.

  공통 기능 = 작은 독립 커밋 + cherry-pick
  V2 기능   = market-direction-v2에만 별도 커밋
  DB 변경   = 적용 이력 보존 + migration 번호 충돌 방지
  배포      = main/V2의 Compose, 포트, DB, volume, network, schedule 완전 분리
  검증      = 양쪽 브랜치에서 각각 수행

이 방식이면 main의 안정성을 유지하면서도 공통 기능을 두 브랜치에 동일하게 반영할 수 있다.
